## 2. 真实链路与排除项

计入准确率的每一次点击都经过：

```text
真实 Computer Use 会话

  -> 生产 Windows SendInput
  -> 测试窗口真实 WM_LBUTTONDOWN / WM_LBUTTONUP / Click
```

没有用独立 SendInput 脚本、DOM/CDP 注入、`PerformClick`、窗口消息伪造、fake backend 或 stub 来替代成绩。夹具自检的独立 SendInput 单独列出，不计入 57 个样例。

## 3. 夹具

`fixture-window.ps1`：

- 独立 WinForms 窗口，本轮标识、题号、目标文字、左侧红色“停止测试 (STOP)”；
- 按钮只改计数、显示结果、写本轮 JSONL；无链接、无文件浏览器、无业务动作；
- 控件 `Bounds` 就是命中矩形，没有外扩透明热区；
- 布局每题冻结；点击后只更新计数和结果，不移动目标；
- 记录整个测试区域的 down/up（包括空白处和干扰按钮），以及激活、停止、准备事件；
- 进程级 DPI 感知（PerMonitorV2），坐标是真实物理像素；
- 文件轮询控制，不开端口、不锁鼠标、不装全局 Hook。

控制器在每次投点前检查夹具 state 中的 `guard`：前台 PID、目标中心 `WindowFromPoint` 归属、透明 helper、窗口几何、题号、尝试计数。guard 不通过就中止该题并记录，不为继续测试移动/关闭个人窗口。

需要区分：

- **夹具/控制器保护**：前台/遮挡检查、题号与几何校验、每题尝试上限、停止按钮、事件记录。它们不是产品能力。
- **插件已有保护**：overlay/彩带隐藏、目标点 elevated-window 检查、坐标换算、按下后 `finally` 释放、前后台窗口选择。它们不因本轮夹具而改变。

夹具自检结果见 [selfcheck-194356](../.zcode/evidence/click-accuracy-0217/selfcheck-194356/selfcheck.json)：DPI 192、物理窗口 1400×900、目标 down/up/激活、空白点击无激活、重新准备重置、停止按钮生效，全部 `true`。这次自检用直接 SendInput，**不计入**真实点击准确率。

## 4. A 组：给定坐标，测插件落点

27 个样例 = 9 个窗口内位置 × 3 种布局：

| 布局 | 窗口物理矩形 | 说明 |
|---|---|---|
| L0 | (1150,380) 1400×900 | 原位置 |
| L1 | (1550,680) 1400×900 | 移动窗口 |
| L2 | (950,300) 1600×1000 | 改变尺寸 |

每个布局的 9 个目标中心相对窗口为归一化 `x ∈ {150,500,850}`、`y ∈ {360,500,800}`，覆盖中心、四边附近和四角附近。目标按钮 220×140 物理（110×70 DIP）。测试程序独立计算目标中心，再由实际提交的坐标和夹具物理窗口独立换算期望落点；没有复用插件坐标函数。

**结果：27/27 首次成功。**

| 指标 | 值 |
|---|---:|
| 指定坐标与实际提交一致 | 27/27 |
| 实际落点相对期望的 X 中位绝对误差 | 0 px |
| Y 中位绝对误差 | 0 px |

逐题 `dx/dy`、实际 click 参数、down/up/激活、前后回图在 `trials/<trialId>/result.json`。

**0px 的计算依据和限制：** 9 个坐标被选成整数物理映射，例如 L0 的 `150/1000 × 1400 = 210`、`360/1000 × 900 = 324`，所以期望落点本身就是整数；插件用 `Math.round` 后与真实事件完全相同。这个结果证明这 27 个点的“提交坐标 → 物理落点”一致，但**不能单独证明任意小数坐标的取整行为**；本轮没有另外构造分数坐标样例。

## 7. 失败、中止与已知误点

本轮的 57 个真实样例：**首次失败 0，中止 0，无事件 0**。因此没有本轮失败样例的截图/坐标可列；这本身是结果，不是静默丢弃。

夹具自身的问题单独记录，不计入 57：

- 第一次自检 `selfcheck-194333` 在 `prepare` 之前读取默认窗口，误报 `physicalWindow=false`；修正为读取 prepare 后的窗口后，`selfcheck-194356` 全部通过。这是自检脚本的检查顺序问题，不是夹具点击路径或生产插件问题。
- 早期 dry-run / probe 只用于确认工具链，未计入正式样例：dry-run 用 `pwsh` 读取过截图尺寸；probe 点到过已结束、已禁用的自检目标。正式 A/B 会话的审计结果是只有 `click`（见第 2 节），没有沿用这些未计分尝试。
- 第一轮 `baseline-0217-193246` 的 B 小/密集编号从 02 开始，是计划生成器的编号偏移；主基线 `baseline-0217-193852` 已用修正后的计划，编号为 01–10，结果计数不变。

用户此前复核过的账号附近误点不属于本轮 57 个样例，单独保留：

- 模型连续使用纵坐标约 932 点击账号附近；
- 当时完整回图中头像中心约在归一化纵坐标 960；
- 改为 `[50,960]` 后账号菜单正常打开；
- 分类：**模型选点偏高**，约 28 个千分比单位。**勘误：** 原写“在 2064px 高工作区上约 58px”不正确；应按当时截图高度约 1641px 计算，`28/1000×1641≈46px`（详见 [docs/17](17-click-accuracy-correction-0217.md)）。不是插件把 960 送错，也不是 DPI 换算。

本轮 B 组没有复现这类误点：B 的目标最小高度为 120px 物理（小按钮）或 64px（菜单行），模型最大派生偏差 12.4px。与头像相比，这些目标仍偏大、文字也更清楚；**不能据此说账号附近的小目标不会误点**。

## 10. 结论与最小建议

**本批证据支持的结论：**

1. 在 27 个给定坐标点上，0.2.17 的提交参数、换算、实际落点、按下/释放/激活全部一致，误差 0px；没有发现 DPI、窗口移动或尺寸变化导致的输入后端偏移。
2. 在 30 个清楚可辨的截图目标上，模型首次全部选中；没有出现“落点在目标内但控件不响应”或重复按下/遗漏释放。
3. 本批没有复现用户偶发误点。已知账号误点仍是模型选点偏高，插件换算不是该次的解释。
4. 57/57 只说明这批样本；不能据此宣称长期零误点。

**最小建议（本轮不实施）：**

- 不基于本批结果修改生产坐标换算或 DPI 逻辑；没有证据支持。
- 若要让现场误点可判分，最小改动是让 click 工具结果带上“实际提交的物理点/观察窗口物理原点”，这样下次误点可直接区分模型选点与后端偏移；这是诊断字段，不改变点击行为。
- 对头像、账号菜单这类更小/更拥挤的真实目标，另建 avatar 尺寸（约 40×20 DIP 或更小）和贴近屏幕边缘的压力样例；不要用本轮大/中目标的全命中替代。
- 若要降低模型选点偏高，优先考虑“点击后验证菜单是否真的打开，未打开则最多纠正一次”的会话策略，而不是继续调坐标换算；这需要单独设计和验证。
